# Roblox technical architecture (planned)

> **Current design / implementation boundary:** [GDD.md](GDD.md) describes the selected five-day, 1–4-player survival direction. The architecture and implementation descriptions below primarily document the older A01 prototype. They are historical or existing-code descriptions, not evidence that the new survival systems, persistence or four-player play are implemented. New work must remain server-authoritative and follow [SURV acceptance criteria](ACCEPTANCE.md). CR-014 and instructor/team review track the design transition.

## Data ownership

`WaveComposition` assigns the selected grace-period creature/machine/Mimic totals and provisional normal-wave proportions. Wave enemies have distinct combat types and health but share prototype AI. Retreat moves toward an outward point, attempts a path around an obstacle, then dissolves; visibility-aware removal and map-wide navigation remain unfinished (CR-016). Studio assertions checked all four party-size compositions; a partial solo spawn snapshot contained all three visual types. Full spawn and behavior remain unverified (SURV-02/07/11).

The helicopter server refreshes physical boarding membership immediately before vote requests and departure; early departure sets the actual clock to Departed. A controlled Studio test verified that a player stepping off immediately before departure is LeftBehind. Multiplayer and other deadline races remain untested (SURV-11).

`HelicopterService` supports a validated saved boarding roster and an explicit post-life-restore placement callback. Absent saved members remain eligible for Disconnected results, not automatic rescue. The world-load coordinator and downed rejoin support are not yet integrated (SURV-10/11).
- **Workspace:** camera-visible map, NPC instances, physics crates/plates and triggers.
- **ReplicatedStorage:** shared constants and minimal RemoteEvents/state snapshots.
- **ServerScriptService:** authoritative AI, combat, missions, round clock and validation.
- **ServerStorage:** private NPC templates, restricted assets and authoritative prefabs.
- **StarterPlayerScripts:** player input/controller/camera and local sound/VFX.
- **StarterGui:** HUD/menu/results.

The survival migration sequence and first inventory slice are tracked in [IMPLEMENTATION_PLAN.md](IMPLEMENTATION_PLAN.md). `Inventory.luau` is a server-side value object now used by the prototype medkit slice; it is not yet the complete shared survival inventory (SURV-05/08).

`DailySupply.plan` calculates an ordered day-2-and-later allocation using connected-player count and aggregate outside/base free capacity. It honors water/food/ammo priority, daily rotating ammo order and the base share of actual allocated items. `DailySupply.points` distributes that plan across supplied point stocks under a per-point cap of 10 without mutating inputs. Neither function selects real locations, changes world stock, persists processed days or integrates with gameplay; the caller must perform atomic item creation and persistence (SURV-05).

`DailySupply.replenish` produces a copied test stock snapshot and processed-day value together and rejects repeated/older days; its stock strings are planning data, not persistent item identities. No actual world item creation or durable commit is implemented (SURV-05/10).

`SessionLife` records a departing player's remaining respawns, health and elimination in memory for the current server. A living return is placed at the active base or fallback spawn; isolated record tests passed. Real reconnect, disconnected downed state, gun ownership, host pause and durable persistence remain open; an offline downed player is not currently retained for rescue (SURV-10).

`PlayerLifeService` exposes a server-only partial snapshot for connected and recorded departed players and accepts validated living/eliminated life records on initialization. `SessionLife` validates and copies its records; capture refuses downed players and refuses the rest of the session after an offline downed state is lost. It is not connected to durable saving or a complete life-state restore (SURV-08/10).

While a server stays alive, `MedkitService` now moves a departing player's firearm tools and server state to a private ServerStorage folder and restores them to that user's backpack on reconnect; it cancels pending reloads. Studio verified initialization and firearm core checks only. Real reconnect, bag ownership, offline downed handling and durable weapon persistence are untested or absent (SURV-10).

`MedkitService` now consumes day events to create shared pickups at five rotating existing floor anchors using `DailySupply.points`; existing spawned items count toward the ten-item point cap and the processed day is held in memory. A controlled solo Studio day-2 event created 11 items in the selected proportions and ignored a duplicate event. Actual pickup, selected-point usability, multiplayer, initial stock integration and durable save/resume remain unverified or absent; earlier notes that no world items are created are superseded (SURV-05/10).

`SurvivalClock` is a deterministic server-side schedule value object covering the selected five day/night lengths, post-night signal deadline, grace warnings/starts/retreats, signal, rescue wait and boarding deadline (SURV-01/02/11). It returns ordered events to a future world controller, and does not itself spawn enemies or rescue players. A Studio Play server assertion test passed; it is not connected to `RoundService`, which still runs the A01 15-minute gate sequence. Save/resume, pausing and in-world events remain unimplemented.

Update: `RoundService` now advances this clock and replicates its phase, day and remaining time; the legacy gate exit and 15-minute timeout are disabled. This is not a playable complete survival run: no gameplay signal exists, and clock events are not connected to waves, lighting, supplies or the helicopter. A session will reach the signal deadline and lose until those systems are implemented. Saving and pausing remain unimplemented.

`RoundService.Start` can receive a validated clock snapshot for supported quiet phases and returns a capture callback. It does not load the rest of the run; wave-night and active-wave snapshots remain unsupported and complete host save/resume is not enabled (SURV-02/10/11).

The server now also derives `Lighting.ClockTime` from the clock's phase and remaining time. Day interpolates 06:00–18:00, night 18:00–06:00; post-night phases remain at 06:00. The earlier statement about lighting is superseded. Visual readability and full real-time transitions have not yet been verified (SURV-02).

`RescueObjectives` assigns temporary power, frequency and transmitter stations to random candidate building floors and validates each prompt on the server. Shared flags gate the transmitter prompt, whose callback signals the clock. `RescueMap` shows server-supplied station coordinates over building bounding boxes. Play verified assignments and the server-side signal gate with controlled flags, but not player interaction, map accuracy, candidate reachability, saves, multiplayer, or the full rescue sequence. A signaled run cannot yet complete because helicopter boarding and results are not implemented (SURV-01/11).

Update: a controlled Play session completed all three temporary prompts and sent the signal using client input after teleporting and temporarily disabling nearby competing prompts. The landing-pad prototype and result handling now exist, but full rescue, natural access, prompt overlap, save/resume and multiplayer remain unverified.

The clock's Boarding and Departed phases now drive `HelicopterService`: a temporary landing pad at the football field tracks connected players' position and marks the group win if anyone is aboard at departure. `PlayerLifeService` prevents damage while aboard. Controlled server testing verified a single player gets `Rescued` at a test pad, but not the real clock-driven sequence or immunity. Disconnected results, early vote, host resume, presentation and multiplayer remain open; the earlier statement that no boarding exists is superseded (SURV-11).

Early departure now has a provisional warning and vote UI; the server requires an aboard initiator to request the warning, counts only aboard voters, cancels a vote on roster change, and ends it at ten seconds or strict majority. A controlled one-client server test rejected a start without warning and accepted solo confirmation. Multiplayer, timeout races, disconnect and resume remain unverified; disconnected individual results are not yet persisted (SURV-11).

The clock emits each selected normal night-wave warning and start, and calculates the GDD's party-scaled total and active cap from a supplied 1–4-player snapshot. It provisionally spaces starts evenly and warns 30 seconds ahead. Actual snapshot timing, spawn pacing, retreat and capped live enemies are not implemented or validated (SURV-02).

The clock detects when an update reaches an event boundary rather than relying on floating-point equality; a Studio simulation of 60,000 fractional updates observed all 11 normal warnings and starts and the signal deadline. This does not verify actual wave behavior (SURV-02/11).

`WaveService` now consumes clock events and creates provisional attackable blocks near the selected base. It snapshots connected non-eliminated players, observes a shared active cap, moves directly toward players or base, checks line of sight before damage, and displays a text warning. A controlled single-player test spawned ten and removed them on retreat. This is a temporary approximation: direct movement can be blocked, no-base and overlapping waves can omit spawns, retreat uses timed removal, and required enemy types, warning sound, complete pacing, multiplayer and performance remain open. The previous sentence about no live consumer is superseded (SURV-02/07).

Wave attackers now clone one of three existing creature gallery models, remove any scripts, make their visuals non-interactive, and attempt a Roblox path when blocked; the simple root is still the combat target. A controlled Studio run verified 10 attackers received visuals and were removed by retreat. Navigation, animation, rig orientation, creature/machine behavior, wave pacing and performance remain untested; earlier block-only/direct-only descriptions are superseded (SURV-02/07).

When a provisional wave stays at its cap for 20 seconds, `WaveService` marks enough existing attackers to retreat for remaining spawns; they count toward capacity until removed. Gunshots provide an eight-second investigation position to wave creatures within the server-supplied radius, unless an active player target takes precedence. Controlled Studio checks observed 24 solo night-5 spawns with peak 20, and noise received at 59 of 60 studs. Pathfinding through walls, visual retreat, overlap, timing, co-op and performance remain unverified (SURV-02/07).

`Firearm` provides server-side pistol/shotgun/rifle loaded counts, compatible ammo-box identity, reload/fire intervals and shotgun falloff (SURV-08). A temporary pistol pickup near B4 is now connected to the existing inventory and raycast path: the server validates equipment, state, ammo and fire interval, and uses 25 enemy or 5 teammate damage. Studio tested a single pistol reload and hit plus malformed direction and rapid-fire rejection. Shotgun/rifle, gunshot noise, survivor Trust, authoritative persistence, drops, and co-op remain incomplete or untested.

The same prototype path now includes a temporary rifle with held-fire client input; the server checks its equipment, rifle ammo, 0.15-second cadence and ray hit, and emits a 120-stud hearing event. Studio Play confirmed its pickup and ammunition appear and core firearm assertions pass; pickup interaction and end-to-end rifle use were not verified. Weapon ownership, respawn and persistence remain unresolved (SURV-07/08).

The temporary shotgun uses six narrow server raycasts and accumulates their damage per target. Team damage is applied once per target and Trust once per shot. Its reload task processes individual shells and a generation number invalidates old reload tasks on fire or unequip; transferring the selected ammunition box cancels the reload. The fixed spread and complete gameplay path remain untested (SURV-08).

`MedkitService` also creates three temporary native ammunition-box pickups near B4 with initial pistol/shotgun/rifle counts of 20/10/30, using the existing server pickup validation and inventory. Pistol pickup was verified in one-client Studio Play. Other ammo types, actual reloading, co-op and final supply placement remain untested (SURV-05/08).

`BaseService` generates one temporary selection prompt per detected campus building floor and stores the selected name in `FNABKRoundState.ActiveBase`. The server checks living state, six-stud range and line of sight. Co-op proposals announce for 10 seconds before the designated host may confirm; the server rejects early, non-host and stale IDs and cancels when host leaves. The one-player shortcut requires the player to be the known host, so a guest left alone cannot claim the base. In Studio the first test player is assigned as host for local testing and is not replaced on disconnect. Published sessions have no first-join fallback: an authoritative host lobby must provision `HostUserId`, which otherwise stays zero. Studio Play tested solo B4, the isolated proposal state machine and a controlled different-host rejection; two-client behavior remains untested. Floor-center points are not verified entrances; respawn, storage, upgrades, saving and full accessibility are not implemented (SURV-03/04).

`BaseService.Start` can initialize a validated active building and returns a server-side capture callback. It rejects a missing, duplicated or floorless building; the full world-save coordinator and real resume remain unimplemented (SURV-03/04/10).

Update: a Roblox private-server owner can now supply the host identity through the server's `PrivateServerOwnerId`; an explicitly provisioned host takes precedence. Public and reserved servers without such an owner still require trusted lobby provisioning. Actual private-server behavior and session persistence remain untested (SURV-03/10).

`MedkitService` now provides separate provisional eight-slot storage at each generated building anchor. Server-side transfers validate player state, proximity, line of sight and inventory/storage revision, using the same item transfer operation as player sharing. Studio Play initialized 23 storage points and the inventory UI; live transfers, concurrent users, storage upgrades and persistence are untested. The earlier statement that no storage exists is superseded (SURV-03/04).

Update: each building can spend two Scrap to expand its in-memory storage to 16 slots; player inventory remains eight slots. A solo Play interaction and isolated capacity test passed. Real expanded-slot transfers, multiple users, layout and durable saves remain untested.

## Trust boundary

`SurvivorHealth` is a server-only shared hit path for baton and prototype pistol targets (SURV-13). It tracks prototype survivor health as model attributes and schedules one recovery on incapacitation; clients cannot choose damage. The current pose assumes anchored graybox students. The 60-second timer is not yet persisted or tied to session pause, and self-defense and survivor interactions remain unimplemented.

`SurvivorHelp` can capture and restore Trust and the exact set of named survivors' health, remaining incapacitation time, daily-help day, food-quest flag and trade count. It validates all records before mutation and refuses defending NPCs because defense timers are not persisted. Host pause and full save integration remain unfinished (SURV-10/13).

Survivor trade stock and wary-tier quota use NPC attributes included in that snapshot; the food-quest prompt follows the completion attribute. A controlled solo prompt test after applying a snapshot verified exhausted stock and wary quota reject a trade without consuming Scrap, and normal Trust releases remaining stock. Full world reopen and multiplayer remain unverified (SURV-10/13).

Update: a controlled solo Play client attack caused survivor damage, Trust loss and retaliation; returning within range reset the disengage interval. Normal movement, firearms, co-op and visual behavior still need testing.

`PlayerLifeService` cancels a revive hold when a validated attack reaches its damage entry point and samples the rescuer's distance, line of sight and state every 0.1 seconds during the hold (SURV-09). ## AI agent boundary
For SURV-05/10, `SessionSupplies` can serialize and validate all recorded player inventories, needs and shared starter claims together. Its restore path can also validate caller-supplied containers against those inventories in the same pass, rejecting duplicate item IDs and returning independent copies. The caller must include every storage and bag, and separately account for world pickups and weapons before committing a complete world. This component is not connected to durable saves.

`MedkitService` exposes an internal server-only partial capture of player supplies, building storage, recovery bags, firearms and uncollected supply and firearm pickups. Pickups receive server-generated IDs before collection, retained when transferred. The capture records the processed supply day, daily point/slot and curated visual identity; `SessionSupplies.restoreBuildings` validates IDs across recorded locations and returns detached state without applying it. A world-save coordinator, pickup visual restoration and other required systems remain unfinished (SURV-04/05/08/10).

For SURV-05/10, `MedkitService.Start` also returns a one-time fresh-service callback to restore validated daily pickups and the processed day. It deliberately does not restore the rest of the captured state and must only be used as part of a complete world-load coordinator.

The same service returns B1 barricade capture and one-time restore callbacks, including occupied-doorway rejection for a solid restored defense. Other buildings and full world persistence remain incomplete (SURV-04/10).

For SURV-07/08, `EnemyHealth` validates server-side damage and updates Mimic-specific or generic enemy health/state attributes. `CombatService` and firearm handling share this path; wave enemies initialize their own type and prototype health. Distinct AI and full combat verification remain pending.
